Apprentissages Critiques — Niveau 1

Ce que j'ai fait & Pourquoi

Dans le cadre du module R108, j'ai utilisé un système Linux (Debian) en ligne de commande pour réaliser des TPs d'administration : navigation dans l'arborescence, manipulation de fichiers, gestion des droits, des processus et des variables d'environnement. L'objectif était de maîtriser les outils fondamentaux d'un environnement Unix pour être autonome sur un poste professionnel.

Comment je l'ai fait

J'ai travaillé directement dans un terminal bash sous Debian. J'ai utilisé des commandes comme mkdir, cp, chmod, find, grep, sort, cut, ps et kill. Les exercices du TP4 (filtres de texte), TP5 (processus) et du CTP m'ont permis de pratiquer ces outils dans des contextes variés et progressifs.

Difficultés & Apprentissages

La diversité des commandes et de leurs options rendait difficile la mémorisation au départ. J'ai appris à utiliser man et --help systématiquement pour comprendre les options disponibles, ce qui m'a rendu beaucoup plus autonome que d'essayer de tout retenir par cœur.

Comment je ferais autrement

Je tiendrais un fichier de notes personnelles (cheatsheet) regroupant les commandes les plus utilisées avec des exemples concrets, pour gagner du temps lors des TPs suivants et consolider ma mémoire pratique.

Preuves d'utilisation du système (R108)

Ce que j'ai fait & Pourquoi

Lors du contrôle de TP en Python (R108), j'ai lu, analysé et modifié des programmes existants : un script d'analyse d'adresse IP, un script de traitement de liste avec calcul de moyenne, et un script de génération de carré ASCII. L'objectif était de comprendre du code écrit par autrui, d'identifier les erreurs et de l'adapter à de nouvelles contraintes.

Comment je l'ai fait

J'ai exécuté les programmes dans le terminal Python3, lu les messages d'erreur pour localiser bugs (SyntaxError, IndexError), puis modifié le code source avec un éditeur texte. Pour le script d'adresse IP, j'ai ajusté la logique conditionnelle en testant différents cas (réseau, broadcast, machine).

Difficultés & Apprentissages

Comprendre la logique d'un programme qu'on n'a pas écrit soi-même prend du temps. J'ai appris à lire le code de bas en haut (variables, puis fonctions, puis flux principal) et à ajouter des print() temporaires pour tracer l'état du programme à différentes étapes.

Comment je ferais autrement

Je commenterais le code au fur et à mesure de ma lecture pour noter ce que chaque bloc fait, avant même de chercher les erreurs. Cela aide à garder une vue d'ensemble et à ne pas modifier un bloc utile par accident.

Ce que j'ai fait & Pourquoi

En R108 (TP6 et CTP), j'ai traduit des algorithmes décrits en langage naturel en scripts bash fonctionnels : un script ldir séparant fichiers et répertoires, un script sauvegardeTxt copiant automatiquement les fichiers .txt, et un script poubelle déplaçant des fichiers vers un répertoire trash. L'objectif était de passer d'une logique abstraite à un programme exécutable dans l'environnement Linux.

Comment je l'ai fait

J'ai rédigé les scripts avec nano sous bash, en utilisant les structures if/else, for, while et des commandes comme find, cp, mv. Pour ldir, j'ai utilisé find -maxdepth 1 avec -type f et -type d séparément, puis trié la sortie avec sort. Chaque script a été rendu exécutable avec chmod +x.

Difficultés & Apprentissages

La gestion des cas limites (pas d'argument fourni, répertoire inexistant, fichier déjà présent en destination) était la partie la plus délicate. J'ai appris à systématiquement tester les cas d'erreur en plus des cas normaux, et à utiliser $# et $? pour contrôler le flux d'exécution.

Comment je ferais autrement

J'écrirais d'abord le pseudo-code sur papier avant de coder, pour identifier tous les cas à traiter sans être distrait par la syntaxe. Cela éviterait d'oublier des cas limites qui sont plus faciles à repérer à la phase de conception qu'à la phase de débogage.

Ce que j'ai fait & Pourquoi

Dans le cadre de la SAÉ portfolio, j'ai conçu et développé ce site web de portfolio avec HTML, CSS and Bootstrap. L'objectif était de comprendre comment s'articule un site web : structure HTML (balises sémantiques, liens entre pages), feuilles de style CSS, framework Bootstrap pour le responsive, et JavaScript pour les interactions (accordéons, modales, navigation mobile).

Comment je l'ai fait

J'ai utilisé un template Bootstrap (BootstrapMade "Personal") comme base, que j'ai personnalisé intégralement : thème sombre, structure multi-pages (portfolio.html, administrer.html, etc.), composants Bootstrap (collapse, accordion, modal) pour afficher les preuves et les codes. Le site est hébergé sur GitHub Pages avec un déploiement continu depuis le dépôt.

Difficultés & Apprentissages

Les différences de rendu entre l'environnement local et GitHub Pages (chemins sensibles à la casse, ressources bloquées) ont nécessité plusieurs corrections. J'ai compris l'importance de tester régulièrement sur l'environnement de déploiement cible, et pas uniquement en local.

Comment je ferais autrement

Je définirais l'arborescence complète du projet (pages, assets, PDFs) avant d'écrire la première ligne de HTML, pour éviter de devoir corriger tous les chemins relatifs après coup quand la structure évolue.

Ce que j'ai fait & Pourquoi

Dans le TP1 du module R207 (Bases de données), j'ai créé et peuplé des tables PostgreSQL à partir de fichiers CSV. L'objectif était de choisir le bon type de données pour chaque colonne (entiers, chaînes, dates, clés étrangères) et d'argumenter pourquoi PostgreSQL était adapté : robustesse des contraintes d'intégrité, facilité des imports CSV, et commandes de sauvegarde/restauration (pg_dump, psql).

Comment je l'ai fait

J'ai créé les tables avec CREATE TABLE en définissant les types (INTEGER, VARCHAR, DATE) et les contraintes (PRIMARY KEY, FOREIGN KEY, NOT NULL). J'ai importé les données via \copy dans psql. Pour la sauvegarde, j'ai utilisé pg_dump depuis le terminal et psql pour la restauration.

Difficultés & Apprentissages

La confusion entre le contexte terminal et le contexte psql (les commandes \copy et pg_dump ne s'exécutent pas au même endroit) a causé plusieurs erreurs. J'ai appris à bien distinguer les commandes SQL (dans psql) des commandes shell (dans le terminal), ce qui est fondamental pour éviter les erreurs d'exécution.

Comment je ferais autrement

Je noterais dans mon compte-rendu pour chaque commande si elle s'exécute dans psql ou dans le terminal, afin de ne plus mélanger les contextes. Un simple rappel visuel (ex: prompt =# vs prompt $) suffit à éviter ces erreurs récurrentes.

Ce que j'ai fait & Pourquoi

Pour la SAÉ portfolio, j'ai publié et versionné mon site sur GitHub Pages, ce qui constitue un environnement de développement collaboratif standard dans le milieu professionnel. L'objectif était de maîtriser les bases de Git (commits, push) et de comprendre le déploiement continu d'une application web statique.

Comment je l'ai fait

J'ai créé un dépôt GitHub, organisé les fichiers selon une arborescence claire (assets/, portfolio/, css/, pdf/), puis utilisé Git pour versionner chaque évolution du site. GitHub Pages publie automatiquement la branche principale à chaque push, ce qui m'a permis de tester le rendu en conditions réelles.

Difficultés & Apprentissages

Les différences de rendu entre l'environnement local et GitHub Pages (chemins sensibles à la casse, ressources bloquées) ont nécessité plusieurs corrections. J'ai compris l'importance de tester régulièrement sur l'environnement de déploiement cible, et pas uniquement en local.

Comment je ferais autrement

J'utiliserais des messages de commit plus descriptifs dès le début ("Ajout AC13.01 programmer" plutôt que "update") pour pouvoir retrouver facilement une version antérieure en cas de régression, et pour habituer à des pratiques professionnelles de versionnement.
